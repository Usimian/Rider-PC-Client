## Open -- correctness, most severe first

### Stops and safety
1. **Web E-STOP can say "STOP SENT" over a dead link** -- `pi/web/mqtt-lite.js` (~l.87) sends PINGREQ but never
   checks PINGRESP, so `connected` stays true on a half-open socket; `app.js` (~l.101, 171) keeps E-STOP enabled
   and reports success on a local `ws.send`. Silent WiFi death -> the stop is lost and shown as sent.
2. **PC GUI E-STOP gives no feedback** -- `gui/core/app_controller.py` (~l.246): disconnected = console print
   only; connected = publish result ignored; keepalive 60 s, so a dead link reads "connected" for up to ~90 s.
3. **Stale ToF limit never noticed by the joystick** -- `pi/rider_controller.py` (~l.196-201, 408): the last
   retained `fwd_factor` is used with no age check; `pi/rider_tof.py` (~l.272) has no frame timeout, so a hung
   sensor never restarts. Obstacle stop on + sensor hangs while clear -> full speed into the next wall; hangs
   while near something -> forward blocked, and the web switch can't release it.
4. **DS4 liveness check can disarm itself** -- `pi/rider_controller.py` (~l.148-159, 177): an OSError on the
   motion-sensor read closes the handle and "no handle" then counts as alive; the sensor device listed late is
   never armed. A silently dead DS4 then keeps re-sending its last stick every 0.5 s past the firmware watchdog.
5. **Bridge never retries a failed broker connect** -- `pi/rider_status_screen.py` (MQTT setup, ~l.300): a
   failed connect sets `mqc = None` for good; the process lives on, so systemd never restarts it. Robot runs
   screen-only, every remote command dropped.
6. **Bridge command queue waits behind slow work** -- `pi/rider_status_screen.py` main loop: the queue is drained
   once per pass, after `bluetoothctl` / `vcgencmd` subprocesses with 1 s timeouts. A slow bluetoothd delays the
   0.5 s `dv` heartbeats past the firmware's 1 s watchdog (brake, lurch) and an E-STOP by ~1 s. Watch `dwd`.
7. **Deploy partial failure** -- `pi/deploy_bridge.sh`: programs are scp'd over the live files first; a later
   failure under `set -e` exits before units, restart and `sync`. Fix: `trap 'sync' EXIT`, and/or stage in /tmp.
   Also it never removes web files deleted from `pi/web/`.
8. **ToF governor's "clear on exit" may never go out** -- `pi/rider_tof_safety.py` (~l.226): QoS 0 publish then
   `loop_stop()` at once; a retained factor 0 can strand forward drive.
9. **Camera can lock itself out** -- `pi/rider_camera.py` (~l.50): Picamera2 opened, configure/start raises,
   never closed; every later request "busy", no crash so no restart.

### Firmware
10. **Body roll OFF overrides the get-up's leg hold** -- main.cpp leg section, `modePrev` starts ROLL_LEAN and
    updates only while powered: roll OFF from NVS (or chosen while limp) -> the first powered cycle runs the
    equalize, aiming the legs at ride height through the kick and catch (the failure gLegHold prevents).
11. **`en 1` while balancing re-zeroes odometry under the running controller** -- `setBalance(true)` zeroes
    wheel_x / gPosTarget but not the LQR's `planX` / `lqrHome` or the policy's `polPrevX`: a one-cycle 400 jolt,
    then a drift back to a stale home; on the policy a false runaway cut. Reached by a double press during a
    get-up's catch (the buttons send `en 1` while telemetry still says off).
12. ~~Heading target stale through a fall latch~~ -- moot: the heading hold was removed 2026-11-14
    (docs/heading_hold_removed.md).
13. **`sit` during the get-up's settle window** -- `gLegLowReq` is overridden by `gLegHold`, then state 2 sets
    `gLegHomeReq`: the legs slew up during the tip-back pulse.
14. **Get-up hold uses MID on a failed `legReadPos`** -- one leg rises ~40 counts during the kick.
15. **Stale `gLegLowReq` survives a limp** -- the next normal balance-on goes to the lowest height.
16. **Per-wheel command not re-clamped after the turn differential** -- `uout +/- tn` up to 650 (kick + turn
    more); gUMax is meant as the current limit.
17. **The kick ignores the roll / fall checks** -- a sideways tip mid-kick keeps 400 for up to 250 ms.
18. **Yaw zero taken even when not still** (`calibrateGyro`) -- carried at boot -> heading drift.
19. **IMU read not checked** -- `imuData`: a short I2C read leaves stack garbage in the sample (gyro up to
    ~+-800 deg/s into lqrRate for a cycle -> a wheel jolt). Check `requestFrom()==12`, keep the last sample.
20. **`wheelRead` accepts any LEN with a good checksum** (expect 0x0B); **`servoReadN` has no checksum** and
    exits on the echo for len 1 (the wheel-mode check could read a wrong mode, rare).
21. **`lqrPitch` / `lqrRate` not volatile** -- written on core 0, read up to 4x per cycle on core 1.
22. **The boot `# gcal` line is lost** (sent ~1.3 s after power-up, before the bridge listens) -- check `gbias=`
    in telemetry instead, or re-emit once the link is up.
23. **`pump` truncates commands over 39 chars and still applies them** (the bridge doesn't check length).
24. **loop() latency** -- ~680 chars of telemetry to USB and the Pi link block loop() ~107 ms per line: real
    telemetry ~9 Hz (not 20), commands (E-STOP too) wait up to ~0.1 s; the message queue is not drained during
    the multi-second dumps (> 8 events lost, counted). Consider Serial TX buffers or the Pi link only.

### GUI / tools
25. **GUI Disconnect / Reconnect / Change IP can deadlock the window** -- `gui/communication/mqtt_client.py`
    (~l.93, 130) waits for the network thread on the Tk thread while that thread waits on Tk (threaded Tcl).
26. **GUI Reconnect starts a second client with the same ID** (~l.108-110, 146-150): two clients kick each other.
27. **GUI body-roll label starts "OFF" while the state is `lean`** -- Toggle sends `level 1`, not what it shows.
28. **GUI image requests not matched to its own request ID** -- with the web camera also on, request chains
    multiply; a lost response stalls "Live".
29. **untethered_balance.py / pi_balance_ctl.py open /dev/ttyAMA0 behind the bridge** (and send removed
    commands `ff`, `kp`, `kd`, `pol`). Unreferenced -- delete or fix.
30. `tools/balance/pos_console.py` never parses `ctrl=LQR`; `tools/diag/mqtt_monitor.py` never reaches run().

### Sims (they make decisions and generate firmware data)
31. **Get-up sim starts the plan at ~1/3 of the real speed** -- `sim/getup_sim.py` (~l.150) + `closed_loop.py`
    plan start uses the 0.1 s-smoothed `vel_s`; the firmware re-seeds `lqrV` from the raw axle speed. Every
    get-up travel figure (and the `--catch-amax` study) is skewed; corrected: ~27-30 cm vs the floor's 14-29.
32. **Sim kick never aborts** like the firmware (250 ms / falling back) -- slow get-ups count as "up".
33. **lqr_design / closed_loop label the removed June LQR "as flashed" / "today's gains".**
34. **IMU loop period likely 2.00 ms, not 2.36** (`fw_timing.py`) -- measure with `gImuN` over time.
35. **RL drive training tops out at 0.35 m/s** (`rider_env.py` DRIVE_TRAIN_VMAX) -- the firmware now allows 0.6.
36. getup_sim default `--hand 10` (firmware 15); minor fidelity items: fw_drive dead-band, model accelerometer
    sees the command 4 ms early, ACC_COMP one cycle late, MPC header VMAX 0.45, encoder ignores slip, getup_sim
    judges the fall cut on the true lean, compare_controllers ignores its args.
